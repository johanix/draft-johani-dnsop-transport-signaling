In the document draft-johani-dnsop-transport-signaling-02.md we describe
mechanisms for what was originally called "opportunistic DNS transport signaling"
by use of an extra SVCB record provided by the authoritative nameserver in the
additional section of a response to a resolver. 

In the PDF document TransportSignalling.pdf we try to establish a baseline terminology.

Opportunistic mode gives the
resolver a private (as in encrypted) connection to the auth server. This is referred
to as "P-mode" (for privacy). However, the resolver does
not verifiably know that the auth server is authoritative for the child zone for which
the resolver wants to issue a query. The reason is that the NS RRset in the referral from
the parent is unsigned and hence, may be spoofed in transit by an active attacker.

However, we now know that we also need to be able to express auth server capability
in more detail, in particular auth servers may be concerned about excessive resource
use if all traffic switched to an encrypted transport. Therefore the current proposal
is to use a private SVCB key (tentatively called "transport") with a value in the
format "doq:10,dot:100,do53:0". This should be interpreted as "send no more than 10%
of the traffic over DOQ, 100% over DOT is ok and please send no traffic over do53".
If both an alpn key and a "transport" key is provided in the SVCB then the "transport"
key takes precedence. If only an "alpn" key/value like: 'alpn="dot,doq" is present,
then that should be interpreted as 'transport="dot:100,doq:100". Note that the
'alpn="-do53"' syntax has been deprecated in favour of 'transport="do53:0"' as that
provides more control and aligns with requirements for expressing transport fractions
for DOT and DOQ.

In addition to opportunistic mode there is another connection mode which we refer
to as "private and authenticated", or "PA-mode". For PA-mode to be possible, the
resolver needs to verify that the auth server is an authoritative server for the
exact child zone that the resolver needs to query about. There are two methods of verifying
this. The easiest method is when the zone is signed. Then it is sufficent to query
for the NS RRset, and verify the DNSSEC signature on the response. The slightly
more complex method (needed for unsigned zones) is when the resolver has a PA-mode
connection to one of the parent auth servers. Over this PA-mode connection it is
possible to query the parent nameserver for the NS RRset for the child with protection
against on-path attacks. After that the resolver absolutely knows who the auth servers
for the child are. The remaining part is to query for the TLSA record of the auth server
(which must be DNSSEC-signed and verified) to be able to establish a mutual-TLS
connection to a now known auth server also known to be authoritative for the child zone.
This is a PA-mode connection.

The perhaps strongest argument for both P-mode and PA-mode connections is that they
may be created without modifying any content in either the child zone or the parent zone.
Hence to establish these improved connections only require (limited) effort by the 
operators of authoritative nameservers and resolvers (i.e. not the "users").
